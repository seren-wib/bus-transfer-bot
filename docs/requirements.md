# 요구사항

> 2026-11-01 13:30 KST 개정. 리허설과 1~2단계에서 확정된 변경을 반영. 바뀐 내용은 맨 아래 "변경 이력"에 정리.

## 목표

A→B 버스 경로에서, 타고 가는 노선의 중간 정류장을 전부 환승 후보로 놓고, 걸어서 500m 안의 승강장까지 포함해 실시간 도착으로 다시 계산한다. 그래서 가장 빨리 도착하는 환승 지점을 찾는다.

## 문제 제기

앱은 환승 지점을 하나만 골라서 추천한다. 그 지점에서 실제 대기가 20분이어도 그대로 보여준다. 허브는 승강장 여러 개를 정류장 하나로 뭉갠다. 길 건너나 몇백 m 옆 승강장에서 더 빠른 버스가 와도 따로 찾아야 한다. 더 빠른 환승을 찾으려면 사람이 정류장마다 다시 검색하고 실시간을 따로 열어야 한다. 그 손 작업을 봇이 대신한다.

## 입력

`{출발지 A, 도착지 B, 출발시각 t}`

- 사용자는 "광화문 가고 싶어"처럼 말한다. 출발지 A는 현위치 GPS 좌표(lat, lon)를 그대로 쓰고, 출발시각 t는 지금이다.
- 도착지 B는 장소 검색 결과(좌표 + 네이버 placeid)를 쓴다.

## 지도 앱

- **계산용 데이터: 네이버 지도.** 화면 조작 대신 네이버 지도 JSON API를 호출한다(Playwright 헤드리스 브라우저 컨텍스트, 로그인 불필요). 쓰는 API는 경로 검색, 실시간 도착, 정류장, 노선 상세.
- **비교용: 카카오맵, 구글맵.** 카카오 경로 API는 자동 조회 방지 토큰으로 막혀 있어서 실제 브라우저 화면에서 읽는다. 구글맵은 스크립트로 DOM을 읽는다(gmaps.py).

## 기능 요구사항

- **R1. 기본 경로 수집.** 네이버에서 A→B 대중교통 경로를 받는다. 1순위의 탑승 노선 X, 승차 정류장 s0, 앱 추천 환승 정류장 s_app, 앱 예상 총 소요시간을 기록한다. 카카오맵·구글맵의 최적 경로(전체 최적, 버스만 최적)도 같이 기록한다. 이것이 비교 기준값이다.
- **R2. 중간 정류장 목록.** 노선 X의 s0 이후 정류장 s1~sN을 노선 상세 API에서 뽑는다. A→si 시간은 다음을 합한다.
  - A→s0 도보: 미터를 시속 5km로 환산.
  - s0에서 X의 실시간 대기.
  - 정류장별 승차 시간: 경로 API의 stops[].duration 누적.
- **R3. 환승 후보 생성.** 각 si에 대해 si 자체와 si에서 **걸어서 500m 이내**의 모든 승강장을 후보로 둔다. 같은 허브의 다른 번호 승강장, 길 건너 승강장, 근처 다른 정류장이 다 포함된다.
  - 후보는 si 좌표를 출발지로 한 경로 검색 결과에서 첫 도보 500m 이하인 탑승 정류장으로 찾는다. 찾은 승강장에서도 한 번 더 검색해서 그 승강장만의 직행 노선을 모은다.
  - 승강장마다 유형(광역/간선/지선/직행 등)을 붙인다.
- **R4. 후보별 si→B 검색.** 후보 승강장마다 B까지 대중교통 경로를 검색해 탑승 노선 Y와 예상 승차 시간을 받는다. 버스만, 추가 환승 없는 경로만 쓴다. 같은 구간을 함께 도는 노선(예: 470/741)은 각각 별도 후보로 둔다.
  - **지금 운행하지 않는 노선은 완전히 뺀다(표시만 하지 않는다).** 빠진 노선은 결과·비교·추천 어디에도 나오지 않는다. 기준 시각은 사용자가 그 승강장에 도착하는 시각이다. 다음 중 하나라도 해당하면 뺀다.
    1. 이름·비고가 오늘 운행하지 않음을 나타낸다: "미운행"(예: "토,일 미운행", "공휴일 미운행"이 오늘 요일과 맞을 때), "평일만"·"출근"·"퇴근"(주말·공휴일), "새벽"(새벽 전용, 03:00~07:00 밖. 예: 새벽A741(자율주행)(토,일 미운행)), 심야 "N" 버스(23:00~05:00 밖).
    2. 노선 상세의 운행 달력(startPointTimes의 요일 묶음: 평일/토요일/공휴일)에 오늘 요일이 없다. 일요일은 공휴일 달력으로 본다.
    3. 노선 상세의 첫차~막차 시간(기점 출발 기준, 막차 + 90분까지 통과 허용, 자정 넘김 처리)에 도착 시각이 들어가지 않는다.
    4. 그 승강장에서 실시간 도착 차량도 없고 배차 정보도 없다.
    5. 경로 검색이 지금부터 120분 넘게 뒤의 탑승을 잡는다(예: 일요일 13:30 검색에 다음 날 05:09 새벽A741). 판정은 경로 검색의 계획 탑승 시각이 아니라 사용자 시각으로 한다.
    6. 실시간 도착 상태가 운행 중(RUNNING)이 아니고 차량도 없다.
  - 테스트(tests/test_filters.py): 일요일 기준 새벽A741이 빠지는지 확인한다.
- **R5. 실시간 도착 조회.** 사용자가 **그 승강장에 도착하는 시각**을 기준으로 Y의 실시간 도착을 본다. 그 시각은 arrive_at_si + 환승 도보 시간이다.
  - 도착 예정이 그 시각 이후인 첫 버스를 쓴다. 첫 차를 놓치면 둘째 차를 쓴다.
  - 실시간 차량이 모두 먼저 지나가면 배차간격으로 다음 차를 추정한다.
  - 실시간이 없으면 배차간격의 절반을 쓰고 'schedule'로 표시한다.
- **R6. 총 소요 계산.** `총분 = A→si + 환승 도보(미터÷83.3m/분) + 대기 + si→B 승차 + 마지막 도보(미터÷83.3m/분)`.
  - 도보 시간은 네이버가 준 분을 쓰지 않고 미터에서 직접 계산한다(시속 5km).
  - 환승 횟수 패널티와 안전 여유(마진)는 없다. 항상 가장 빠른 경로를 고른다.
- **R7. 추천.** 총분이 가장 작은 후보 하나를 고른다. 단 **카카오·네이버·구글 최적 경로보다 느리면 안 된다.** 우리 후보가 더 느리면 그중 가장 빠른 지도 앱 경로를 그대로 추천한다.
  - 출력은 `{추천 si, 승강장, 승강장 유형, 환승 도보 m, 환승 노선 Y, 대기 분, 총분, 카카오/네이버/구글 최적 총분, 단축 분}`과 사람이 읽는 한 줄이다.
  - 예: "강남역12번출구에서 내려 494m 걸어 지하철2호선강남역(중)에서 470 타면 총 N분. 네이버 1순위 75분, 카카오 버스만 68분, 구글 53분."
- **R8. 비교 증거.** 지도 앱 최적보다 우리 추천이 빠른 케이스 1개를 화면 캡처한다. 이후 임의 출발/도착 10쌍으로 타 지도 대비 결과를 측정해 발표자료에 쓴다.
- **R9. 승강장 유형 분류.** 노선 유형(광역/간선/지선/직행 등, API의 type.name)으로 판정한다. 순위 계산에는 쓰지 않고 출력에만 쓴다.

## 비기능 요구사항

- **N1.** 네이버는 JSON API 호출을 Playwright 스크립트(naver.py)로 고정한다. 데스크톱 브라우저를 붙잡아 조작하지 않는다. 카카오만 브라우저 화면으로 읽는다.
- **N2.** 검색 상한을 올린다. API 질의가 1회 1초 미만이고 동시 8개까지 돌리므로, 중간 정류장은 노선 전체(예: 15개), 정류장마다 승강장 최대 5개(si + 추가 4개)까지 본다. 실행 시간(N4) 안에 끝나면 된다.
- **N3.** 검색 하나가 실패해도 전체는 죽지 않는다. 실패 후보는 빼고 계산한다(`results/{si}.error.json`).
- **N4.** A→B 한 번 처리 5분 이내. 목표는 1분 이내.
- **N5.** 데모는 미리 돌린 결과 + 캡처. 실시간 시연은 백업.

## 봇 분배

같은 지시문의 검색 봇 3개 대신, 역할별로 나눠 동시에 돌린다.

- **오케스트레이터:** 입력(GPS, 목적지), R1, R2. 작업 파일을 쓰고, 결과를 모아 R6, R7, R8.
- **네이버 검색 워커 1개:** 한 프로세스에서 질의를 동시에 돌려 모든 si에 대해 R3, R4, R5, R9를 처리한다(search_bot.py). 작업 파일을 나눠 여러 개 띄울 수도 있다.
- **카카오 비교:** 브라우저로 카카오맵 A→B 최적 경로(전체, 버스만)를 읽어 기록한다. 네이버 워커와 병렬로 돈다.
- **구글 비교:** 스크립트(gmaps.py)로 구글맵 A→B 경로를 읽는다.

## 봇 간 계약

- `tasks/bot{n}.json` = `[{si, stop_id, ars, a_to_si_min, arrive_at_si(ISO)}]`. 오케스트레이터만 쓴다.
- `results/{si}.json` = `[{platform_stop_id, platform_name, ars, type, walk_m, walk_min, line_Y, line_Y_id, wait_min, wait_source, si_to_B_ride_min, final_walk_m, final_walk_min, si_to_B_total_min, read_at}]`. 검색 워커가 자기 si만 쓴다.
- `results/compare.json`(예정) = 카카오·네이버·구글 최적 경로 `{app, kind(전체/버스만), total_min, summary, read_at}`.

## 리허설(11:20) 확인 결과

- 중간 정류장 목록: 상세보기에 이름은 나오지만 정류장별 시간은 화면에 없다. API에는 있다.
- 실시간 도착: 경로 화면의 탑승 정류장에 같이 뜬다. API로는 정류장·노선별로 조회한다.
- 허브 승강장은 정류장 번호별로 분리되어 있다(사당역 18개+).
- 검색 1회: 화면 약 1~1.3초, API 0.6~0.8초.
- 네이버는 자동 조작 차단·캡차가 없다(장소 검색 API만 브라우저 밖 호출 시 캡차).
- GPS: 동의 후 좌표 획득을 확인했다.
